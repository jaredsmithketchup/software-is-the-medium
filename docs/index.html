Code and data

  • Code says what can happen
  • Configuration tunes it; live state records what is happening
  • Changing a jump setting is not the same as changing the jump logic

ch00 §1.

Speaker card — S6

Say

  • The logic says: if jump is requested and the player is grounded, set upward velocity. The configured jump speed is a value the designer can tune.
  • Current velocity and grounded status are live state. They describe this player now, not the default for every player.
  • Changing jump speed can make a higher jump. Allowing a second jump in mid-air changes the logic. Knowing which change you want saves a lot of random editing.

Show / ask

  • Ask: is ammunition 30 logic or state? State. Is "do not fire with zero ammunition" logic? Yes.

If asked

  • Configuration is also data. The configuration/live-state distinction is about use, not a different physical substance. Code itself is stored as bytes; its role is to supply instructions.

Speaker card — S7

Data-driven: config binds data to code

  • Most engines are data-driven — a config or asset layer declares how data and code connect
  • JavaScript and Python apps read JSON or YAML files to tune behavior without recompiling
  • Unreal Blueprints range from node graphs that run as logic to Data-Only Blueprints that store properties for other code
  • A config edit changes behavior only if the reading code already understands the file

ch00 §1.1–1.3, ch05 §6.

Speaker card — S8

Say

  • Most games and apps are data-driven: values and logic live in files that code reads, bound together by a config or asset layer.
  • A JavaScript or Python application reads JSON or YAML at run time. Change a value and the program behaves differently; the code that reads the file stays the same.
  • In Unreal, Blueprints span that spectrum. A Blueprint graph is node logic that actually runs. A Data-Only Blueprint is just a container of properties that other code reads.
  • The binding only works where the reading code already understands the file. "Data-driven" always means code, data, and a declared connection between them.

If asked

  • This is the career-long question from ch00 §1.3: what belongs in code, and what in data? Unreal's own docs call the property-only case Data-Only Blueprints and recommend them for data inheritance; a graph Blueprint is stored as .uasset data but executes as logic.
  • "Data-driven," "declarative configuration," and "the config layer" are the common names for the pattern. JSON and YAML are examples of a wider family — INI, TOML, DataTables, engine settings files. The relationship matters more than the format: a file the code reads to shape behavior.
  • Epic's Data Assets are related but separate: UDataAsset instances that hold data without being Blueprints at all.

A — SOFTWARE

Frame rate is not response time

  • 60 fps = one frame every 16.7 ms
  • Input-to-display latency spans several stages and may span several frames
  • Smooth output can still respond late

ch00 §3.3–3.4.

Speaker card — S11

Say

  • Divide one thousand milliseconds by sixty. You get about 16.7 milliseconds between frames at sixty frames per second.
  • That is not a promise that your click reaches the screen in 16.7 milliseconds. The device must sample it, the simulation must consume it, rendering must run, and the display must present it. Queues can add waiting.
  • Frame rate measures how frequently images arrive. Latency measures how old the response is. A conveyor belt can deliver frequently while carrying old packages.

Show / ask

  • Trace the chain once. Ask: could a game be smooth but feel sluggish? Yes, because queued work can preserve throughput while increasing response delay.

If asked

  • 120 fps gives 8.3 ms; 30 fps gives 33.3 ms. These are arithmetic intervals, not measured end-to-end latency. Networked actions may include additional network and server delay. Do not sum CPU and GPU frame timings blindly: work can overlap.

A schema says what the data must look like

  • A schema describes the shape, meaning, and limits of data
  • Shape follows the data's intent: .fbx authors, .gltf ships, .mdl runs — three 3D-model formats, three goals
  • Names, types, defaults, and allowed ranges become checkable by any tool
  • Without one, "the file is valid" is only an opinion; JSON Schema, typed assets, and tables all play the same role

ch05 §1, §3–6.

Speaker card — S12

Say

  • A schema is the description of what data must look like: its fields, their types, and what is allowed.
  • With a schema, "this file is valid" stops being an opinion and becomes a check any tool can run consistently.
  • The shape follows the intent. FBX, glTF, and MDL are all 3D-model formats, but each was designed for a different job: FBX for authoring interchange, glTF to ship between tools, MDL for the engine to load fast. Different goals, different schemas.
  • Think of the weapon files: names, units, and ranges. A schema is what makes them machine-checkable before they ever reach a consumer.

Show / ask

  • Sketch a small record: name (string), rounds (integer 0–30), cooldown (seconds). Ask which field could break a handoff if a producer filled it wrong.

If asked

  • Schemas range from implicit convention to formal languages (JSON Schema, Protocol Buffers) to compiled types; the value appears when producer and consumer are separate parties.
  • ch05 §3–4 grounds the example: FBX is the de-facto authoring interchange nobody openly owns, glTF is the open "JPEG of 3D" (indexed and runtime-conscious), and the .mdl family is tied to the engine's renderer. §5 is the rule: each schema is designed for its job, which is why engines convert between them.
  • This is the reference's one-idea from ch05 §1: no data ever works without a declared shape-and-meaning contract. JSON, YAML, and binary forms are all covered in ch05 §6.

Next

  • Whoever writes the data and whoever reads it must share that description. That is a contract.

Contracts bind producers and consumers

  • A contract is the interface between whoever writes data and whoever reads it
  • The producer's output must match what the consumer expects, field by field
  • Contracts spell out names, units, formats, and budgets; changes version the contract

ch05 §1–2.

Speaker card — S13

Say

  • A contract is the interface between the side that produces data and the side that consumes it.
  • The producer's output has to match what the consumer reads, field by field, across every boundary.
  • Contracts carry names, units, formats, and budgets — the handoff checklist you will meet again on the weapon slides.
  • When one side changes, the contract versions: that is why new engine versions, save files, and mods can stop working.

If asked

  • A design document informs a schema; it is not automatically a machine-readable contract. The schema is what both sides can execute against.
  • Version numbers, validation, and changelogs are the working parts of a living contract. Desyncs and protocol mismatches (ch05 §7) are that contract breaking.

A frame is a time budget

  • At a 60 fps target, the interval is 16.7 ms
  • Late work causes a hitch or lower frame rate: games are usually soft real-time
  • Measure the bottleneck; CPU and GPU work can overlap

ch00 §5, ch01 §4.

Speaker card — S18

Say

  • At a sixty-frame target we aim to deliver a frame roughly every 16.7 milliseconds. Illustratively, twelve milliseconds of critical-path work fits; twenty-four does not.
  • Games are generally soft real-time: being late hurts responsiveness or smoothness, but a missed frame is not automatically total system failure. Hard real-time systems require deadline guarantees for correctness.
  • Find the bottleneck before optimizing. A faster shader does not fix a main thread waiting for an asset to load.

If asked

  • CPU and GPU often work on different frames concurrently. Their times are not simply added to predict frame rate. Synchronization, queues, refresh policy, and the critical path matter.
  • In Unreal, start with stat unit for Game, Draw, GPU, and Frame, then a timeline in Unreal Insights. Measure on the target hardware, including slow frames rather than only an average.

The renderer reads state

  • The world is not the picture of the world
  • A server can track hits and health without drawing a frame
  • Rendering may simulate visual effects; that does not make the image the authority on damage

ch01 §3.

Speaker card — S19

Say

  • Think of a scoreboard and the scorekeeper. The display reports a score; it does not necessarily decide which goal counts.

Three ways to organize a world

  • Scene graph: what moves with what?
  • Spatial index: what is near, visible, or colliding?
  • Components / ECS: what data does each thing have?
  • These solve different problems and often coexist

ch02 §1–6.

Speaker card — S20

Say

  • A transform tree answers "what moves with what?" Move a hand and the attached weapon follows.
  • A spatial index answers "what is near or potentially visible?" A BSP partitions space; other engines use grids or bounding-volume trees.
  • Components answer "what data and capabilities does this thing have?" An ECS organizes entities by components and runs systems over matching data.
  • These are not competing brands of world model. One engine can use all three for different jobs.

If asked

  • ECS means entity-component-system. Not every ECS uses the same columnar storage, and not every component-based engine is an ECS. Unreal Actors and Components do not by themselves imply a pure ECS.
  • A spatial index may be derived from world data. If a moving object is not reflected in the index, queries can give wrong answers even when its visible transform looks correct.

Q&A ammunition

  • "Which engine should I learn?" Choose a small achievable project and an engine with accessible tools, documentation, and support for your platform. Complete the loop from authoring to a playable build. Learn one well, then map the next using the same questions.
  • "Does a game need an engine?" It needs software that fulfills the required responsibilities, whether supplied by a general engine, a framework, libraries, or custom code. There is no requirement to buy a branded product.

  • "What should a non-programmer do tomorrow?" Trace one of your own assets from source file through import and reference to its visible or audible result. Record one format constraint, one loading constraint, and one timing constraint.
  • "Where should I read next?" Start with the repository's reference for the relevant question, then check version-specific primary documentation. For engine behavior, prefer source and measured traces over confident summaries, including these notes.
